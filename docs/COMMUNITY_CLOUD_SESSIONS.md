# Approval-gated session prompts

Use one numbered prompt per approved session. Each prompt incorporates the shared contract below. In a new chat, paste the shared contract plus the selected prompt, or instruct the agent to read this file and execute that numbered session. Merely reading this file is not approval. Sessions 01–04 were approved and implemented locally; Session 05 awaits approval. See AGENT_MEMORY.md for current evidence and gaps.

## Shared contract for every prompt

Work on ProblemHunt as my implementation partner and DevOps mentor. Execute only the session I explicitly approve. Read AGENTS.md, docs/AGENT_MEMORY.md, PROJECT_STATE, RELEASE_CHECKLIST, COMMUNITY_CLOUD_ROADMAP and relevant stage material; follow the repository's PDF/audit reading requirements before substantial changes. Inspect Git status, preserve work and use feature/community-knowledge-platform. Reuse current code and valid evidence rather than rebuilding completed features. Distinguish historical docs from verified current state.

Start with a concise scope and success criteria. Work autonomously within this approved scope, with brief meaningful updates. No automatic next session, no agents unless separately authorized, and no unrelated cleanup. Never write synthetic production data or expose secrets. General approval of this session does not authorize pushes, merges, deployments, Azure/domain changes, hosted migrations, data removal or external messages. Prepare concrete plans and diffs before requesting any separate authorization required for those actions.

Use focused searches and checks; run appropriate permission, integration, frontend and visual checks for the actual changes. Do not repeatedly run unchanged checks or claim mocked/local evidence proves cloud behavior. Explain one key concept simply and include a practical failure/recovery exercise where relevant. At completion or interruption update AGENT_MEMORY, PROJECT_STATE and RELEASE_CHECKLIST with actual evidence, limitations, changed files and exact next action. Finish with outcome, tests, remaining gaps and the next prompt for approval. If unfinished, propose continuation of this session. Stop at this session boundary; a usage reset is not approval.

## Session 05 — Docker notification service

Implement discussion following and reliable private in-app reply notifications as one vertical slice. Reuse compatible notification structures. Save durable events in the same transaction as the relevant change, dispatch to a local queue and process using a Docker worker. Define event versions, authorization, opt-out handling, idempotency, retry/backoff and a failed-message recovery path. Include non-root image execution where supported, health behavior, graceful shutdown and a documented local Compose workflow. Keep privileges server-side and limit exposed content. Test worker crashes before/after side effects, duplicate delivery, restart recovery, unauthorized recipients and content hidden before processing. If too large, finish the core vertical slice and save the remaining tests as a continuation; do not claim completion prematurely. No email sending or hosted deployment.

## Session 08 — Local Kubernetes learning lab

Run the same notification image on kind or minikube using a local disposable environment. Choose one manifest packaging approach and explain it. Configure Deployments, required networking, probes, requests/limits, configuration and minimally scoped service accounts/RBAC. Keep databases outside the cluster and secrets out of Git. Demonstrate a bad image, unhealthy readiness, pod termination and a rolling update/rollback. Prove how queued work recovers. Add scaling only with suitable measured metrics; explain why replica count alone does not prove useful throughput. Deliver a reproducible lab, troubleshooting runbook and short comparison with Container Apps. No AKS creation.

Avoid moving the public application or database. Tear down only the explicitly approved lab resources under the approved teardown scope. If declined, mark this session skipped and preserve the local lab; do not block AI evaluation on AKS.

## Session 10 — Evaluated related-case retrieval

Assess whether sufficient eligible genuine content exists. Build a reviewed evaluation set of approximately 30–50 realistic symptom queries when feasible and establish the existing keyword-search baseline. If data is insufficient, deliver an evaluation harness and document the missing data instead of inventing production content or reporting meaningless quality gains. Prototype embedding retrieval in the isolated environment with reviewed data-provider permissions and cost limits. Compare useful-result recall in the first five hits, latency and cost; handle edits, deletions and visibility at indexing and retrieval. Add related-case/duplicate suggestions only if supported by evaluation. Never generate author-accepted answers automatically. Deliver the measured go/no-go recommendation, limitations and a proposed next roadmap requiring fresh approval.
